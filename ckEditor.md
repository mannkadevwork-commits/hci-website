HC Interior CMS: CKEditor & Frontend Architecture


CKEditor is a rich text editor used in the CMS to allow content writers to create formatted content without writing HTML manually. Instead of typing HTML tags, users can write content visually by using headings, bold text, lists, tables, images, links, and other formatting options. CKEditor internally converts everything into HTML, which is then stored in the database and rendered on the frontend.

The implementation in our project is divided into two parts:

1. Structured data handled through React form fields.
2. Rich content handled through CKEditor.

These two serve different purposes.

------------------------------------------------------------

React Form Fields

The CMS contains normal React input fields for information that needs to be stored separately in the database.

Examples include:

- Banner Heading
- Banner Sub Heading
- Banner Image
- Slug
- Meta Title
- Meta Description
- Author
- Publish Date
- Other SEO related fields

These fields are controlled using React state and each value maps directly to a database column.

Example flow:

User enters Banner Heading

↓

React State Updates

↓

API Request

↓

Database stores banner_heading field

Since these values are structured data, they are easier to search, filter, update and use independently on the frontend.

------------------------------------------------------------

CKEditor

CKEditor is responsible only for the main page or blog content.

Instead of using multiple textareas, the content writer creates the complete article inside CKEditor.

The editor allows users to create:

- Headings
- Paragraphs
- Lists
- Tables
- Images
- Links
- Blockquotes
- Embedded content
- Other rich text formatting

As the user writes, CKEditor generates HTML automatically.

For example, if a user creates a heading and a paragraph, CKEditor internally generates HTML similar to:

```html
<h2>Kitchen Design</h2>

<p>This is the introduction of the article.</p>
```

This HTML is sent to the backend and stored in a single content field instead of multiple individual fields.

------------------------------------------------------------

CKEditor Component

Instead of configuring CKEditor separately on every CMS page, the project uses a reusable CKEditor component.

This keeps all editor configuration in one place.

The common configuration includes:

- Toolbar options
- Plugin configuration
- Upload adapter
- Image handling
- Editor settings

Using a single component ensures that every CMS page behaves consistently.

------------------------------------------------------------

Image Upload Process

Image uploads are customized instead of using CKEditor's default upload process.

When a user inserts an image, the following steps occur:

User Selects Image

↓

Image is processed

↓

Alt Text is requested

↓

Image is uploaded through backend API

↓

Image URL is returned

↓

CKEditor inserts the image into the article

↓

Updated HTML is generated

This allows uploaded images to follow the project's backend upload process rather than CKEditor's default storage.

------------------------------------------------------------

Alt Text

The project requires image alt text before completing the upload.

This ensures every uploaded image contains meaningful alternative text.

Example:

```html
<img
src="/uploads/kitchen.jpg"
alt="Modern modular kitchen design">
```

This improves accessibility and SEO.

------------------------------------------------------------

Image Compression

Before uploading, images are compressed on the client side.

Benefits include:

- Faster uploads
- Reduced file size
- Better website performance
- Lower bandwidth usage

This process is transparent to the content writer.

------------------------------------------------------------

How Content is Stored

Banner information is stored as individual database fields.

Example:

title

banner_heading

banner_sub_heading

banner_image

slug

meta_title

meta_description

The article itself is stored as HTML generated by CKEditor.

Example:

```html
<h2>Kitchen Design</h2>

<p>Modern kitchen designs focus on...</p>

<ul>
    <li>Luxury Finish</li>
    <li>Storage</li>
</ul>

<img src="..." alt="Kitchen">
```

------------------------------------------------------------

How Next.js Uses the Content

The frontend does not recreate the article.

Instead, it requests the saved data from the backend.

Flow:

Next.js Page

↓

API Request

↓

Backend Returns

- Banner Data
- SEO Data
- CKEditor HTML

↓

Frontend Displays Banner

↓

Frontend Renders Article Content

For blog pages, the dynamic route receives the content based on the blog slug and renders both the structured fields and the HTML content.

The React fields are used to render sections like the banner, page title, breadcrumbs, SEO metadata and other fixed sections.

The HTML generated by CKEditor is rendered inside the content section of the page, allowing editors to change the article without requiring frontend code changes.

------------------------------------------------------------

Difference Between React Inputs and CKEditor

React Inputs

- Structured information
- Stored as separate database fields
- Used for banners, SEO and metadata
- Easy to query and update

CKEditor

- Rich article content
- Stored as generated HTML
- Handles formatting, images, tables and lists
- Used for the main body of the page

Both work together but solve different problems.

------------------------------------------------------------

Why CKEditor is Used

Using CKEditor allows non-technical users to manage website content without editing HTML directly.

Developers define the page structure using React components, while content writers manage the actual article content through CKEditor.

This separation makes the CMS easier to maintain and allows content updates without requiring frontend code changes.
